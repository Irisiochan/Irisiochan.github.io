要解决的问题

同时用五六个 AI 编程工具时，它们各有各的会话、记忆和权限，互相看不见。让它们协作写代码，常见的毛病是自己写自己评、返工来回空转、tokens 花了没人算账、合入和部署要人一直盯着。

怎么做的

  • 统一网关：7 种后端适配（5 个 CLI、API 直连、一个实验性后端），会话持久化，长期记忆经 MCP 注入（见 Memory Vault）。网关 20 个模块单向依赖，由测试强制无环。
  • 会议室 7 个席位：规划、执行、评审、仲裁、合入、部署、维护。每个席位单独绑定 agent、模型和推理强度。权限取「席位策略 ∩ 任务授权 ∩ 宿主能力」，执行者不能兼任评审。
  • 交棒走工具调用：模型显式调用交棒工具，网关只做校验，不替模型决定下一步。任务账本是唯一的状态来源。
  • Worker：PC 和 VPS 跑同一份代码，只做出站长轮询，按能力心跳接单。默认在 VPS 执行，PC 只保留摄像头、局域网这类设备能力。
  • 部署：拒绝脏工作树 → 只快进 → 构建 → 重启 → 30 秒健康检查，失败自动回滚。

防空转和控成本

  • 执行满 3 轮必须送评审；同一问题 2 次不达标进仲裁，第 3 次停止自动派单、交给人。
  • 评审通过必须附真实 diff 和全绿测试。
  • 每个任务每天最多唤醒 40 次，超出自动转人工；同一任务同一时刻只有一个持棒者。
  • 每次尝试记录轮次、时长、tokens 和唤醒次数，按席位汇总。
  • 机械步骤不占席位：评审通过直接启动合入，干净的 rebase 免重审，部署验证后自动收口。

长期记忆 / 上下文工程 · 开源

Memory Vault

给多个 AI 共用的长期记忆层。Markdown 文件是真源，MCP 暴露 20 个读写工具，结构化事实带版本链，Git 多端同步。Claude Code、Codex、Grok CLI、OpenCode 和 AI Hub 网关读写同一份记忆。

Python 3.12FastMCPObsidianGitsystemdTailscaleGitHub Actions
开源模板 Irisiochan/memory-vault（MIT）可直接 Use this template 建自己的私有记忆库

要解决的问题

每个 AI 各记各的，换一个工具就要重新交代一遍背景。几个 AI 同时写同一份记忆会互相覆盖，还会谎报「已同步」。每轮都去拉一遍上下文，tokens 烧得很快。

怎么做的

  • 分层存储：叙事记忆、结构化事实、待验证收件箱、带截止日期的任务账本、日常流水、软删区。软删满 7 天冷静期才允许真删。
  • 写入分流写进工具说明：稳定的事实走 fact 层，拿不准的先进收件箱，验证后再晋升；有截止日期的进账本。
  • Fact 层：同一个键写入新值时，旧值标记为已取代，形成版本链。每条必须带来源，推断出来的事实不能超过明确事实的 30%。每次写入都在锁内重建精简核心索引，重建失败就不提交。
  • 宿主预注入：会话开始时由 hook 从本地缓存注入核心上下文，每轮注入当前时间；工具说明要求看到这些标记就不再重复调用。缓存过期时退回让模型自己拉。
  • Git 同步：只 add 本次写入的路径 → commit → pull --rebase → push。发现别人已暂存的改动就停下，不替人提交。跨进程文件锁覆盖整个写事务。
  • 部署：VPS 上用非 root 用户常驻，主实例只绑内网并要求 token；给 Web 连接器用的公网入口是另一个只绑回环的实例，经反代暴露。
  • 隐私：原始聊天只留在本机，不进 git、云和服务器；凭据一律写成占位符；公开模板有边界测试，防止私人数据混进去。

少许是多少

把模糊的量翻成数字。主场景是「这杯奶茶多少大卡」和月度账本；辅场景是把菜谱里的「少许、中火、断生」翻成能照着做的卡片。

微信原生小程序微信云开发云函数微信 OCRNode 冒烟测试
尚未上线，计划 10 月提审

选题怎么来的

最早的题目是给宠物寄养店员用的「寄养手记」：拍照加一句语音，生成给家长的寄养日报。我做过两年寄养，痛点是真的。调研后放弃了：门店都有自己的流程和小程序，第三方工具接不进去，也找不到愿意试用的店。于是换成我自己就是目标用户的题目：看不懂菜谱里的模糊词。内测时有用户提出想记奶茶热量，最后合并成现在奶茶为主、菜谱为辅的结构。

怎么做的

  • 答案走规则和数据：菜谱模糊词是 50 个术语（55 个别名）的本地最长匹配。翻译卡每个词给数值、参照、补救三段，并按「厨房档案」换算，比如灶具设成电磁炉，「大火」就显示瓦数。
  • 热量只认官方数据：只用品牌小程序里公示的数据，不跟外链，也不抓要登录的接口。霸王茶姬 120 款、2,130 个档位组合逐项核对过；喜茶 12 款、51 组。其余品牌按品类估算，账本里官方和估算分两行显示。
  • 估算有检验：品类估算用留一法检验，误差中位数 10 kcal（n = 2,121）。
  • 拍点单识别：云函数调微信 OCR 拿文本行，再用规则匹配到官方档位。同一维度识别出多个档位时提示「没看清」，不猜默认值。
  • 不收数据：记录只存在手机本地，不需要账号。

我做的决定

  1. 2026-08-19报名 WAIC 东部赛区，选题「寄养手记」。
  2. 2026-08-27调研后放弃寄养方向，改做菜谱模糊词。
  3. 2026-09-20把奶茶和菜谱两个作品合并，奶茶为主。原因：内测发现长菜谱被截断、长尾词兜不住；第二个 AppID 还要单独备案。
  4. 2026-09-22不硬算糖（品牌都不公示糖的克数），改看热量和碳水。
  5. 2026-09-25视觉大模型要切换到付费计费才能开通。在「切计费 / 改用微信 OCR / 砍掉识别」三个选项里选了 OCR。

图像 / 数据实验 · Phase 0 进行中

可编辑相机风格配方

把理光 GR IV HDF 机内的「负片」风格反推成 Lightroom 里看得见、能改、能复现的白盒配方：一份配方文件，加上显式的 Profile / LUT。

PythonOpenCVSciPyLightroom Classic 插件（Lua）XMPCIEDE2000
私有仓库，报告可按需提供

要解决的问题

需求来自一位用这台相机的朋友。机内风格没有公开参数，只能拿同一次曝光的 RAW 和机内 JPEG 反推。更难的是评估本身：如果 Lightroom 把同一张图渲染两次结果不一样，后面所有拟合数字都没有意义。

怎么做的

  • 先建复现闸：配方 schema → 确定性 XMP（重复生成字节一致）→ Lightroom 在 GPU 关闭、两份隔离副本里各导出一次 → 算 CIEDE2000 色差。门槛 mean ≤ 0.15、p99 ≤ 0.50。GPU 没确认关掉就拒绝启动。同一组显影参数两次导出逐像素一致（196,608 像素，ΔE00 = 0）。
  • 数据审计：自己写 makernote 解析，从 96 张里筛出 92 对负片，并发现其中 90 张拍摄时开着 HDF 柔焦滤镜，记为已知偏差。
  • 反拟合实验：用两个相机配置各渲一遍，ECC 仿射配准（92 / 92 成功），按场景分组做 5 折交叉验证，从简单到复杂比较一串模型。
